# 用 vibe coding 打造 MenuGen

Andrej Karpathy

我经常在餐厅落座、翻看菜单，然后感觉……有点发懵。Pâté（法式肉酱冻）到底是什么来着？Tagine（塔吉锅炖菜）是什么？Cavatappi……是种意面对吧？Sweetbread（直译"甜面包"，实为胸腺）听起来很好吃（我超爱吃甜食）。有时候这事儿真能让人抓狂。"Confit tubers folded with matured curd and finished with a beurre noisette infusion"（油封根茎菜拌陈年凝乳，佐以榛子黄油浸汁）——好吧，所以……这到底是啥？我这辈子花了太多时间谷歌搜食物图片，所以当最近一场 vibe coding 黑客松来临时，我意识到这是一个绝佳的机会，终于可以做出那个我一直想要却无处可寻的应用了。它如今真切地问世了，我把它命名为……🥁🥁🥁……MenuGen：

Screenshot 2025-04-26 at 1

MenuGen 超级简单：拍一张菜单的照片，它就会为菜单上的每一道菜生成图片，把菜单"可视化"出来。显然，这些图并不是那家餐厅真正端上桌的样子，但能让你有个基本概念：这几道是沙拉，这道是鱼，这道是汤，等等。我个人使用下来发现它实在太有用了，于是在黑客松结束之后（我在现场让第一个版本在 localhost 上跑了起来），我又继续 vibe coding 了一阵子，把它部署上线、加上身份验证和支付功能，总之让它变成了一个真正的产品。所以，下次出门就餐时不妨一试 :): menugen.app!

MenuGen 是我第一个端到端全程 vibe coding 出来的应用：我（一个爱折腾、但几乎没有真正的 Web 开发经验的人）从零开始一路做到了一个真正的产品——人们可以注册、付费、从中获得实用价值，而我也能心安理得地赚上 10% 的加价。还挺酷的。不过除了应用本身的实用性之外，MenuGen 对我而言还是一次有意思的探索：探索 vibe coding 应用、以及这条路在今天到底有多可行。正因如此，我没有亲手写过任何代码；100% 的代码都出自 Cursor+Claude 之手，以至于按照我习惯的传统意义上说，我基本上并不真正了解 MenuGen 是怎么运作的。既然项目现在"完成"了（也就是说第一个版本看起来能用了），我想在这篇短文里写下我的体验——如今一个非 Web 开发者要 vibe coding 出一个 Web 应用，是怎样一番景象。

先是本地版本。这在 vibe coding 中算是相当常见的体验：应用的第一版原型在我本地机器上跑起来没花多少时间。我用 Cursor + Claude 3.7，把应用的描述发给它，它很快就写好了全部 React 前端组件，铺陈出一个漂亮的网页——流畅的多彩字体、小巧的 CSS 动画、响应式设计一应俱全，唯独没有真正的后端功能。看着一个新网站如此迅速地成形，是种强烈的诱惑。我感觉自己已经完成了 80%，但（伏笔……）实际更接近 20%。

OpenAI API。麻烦大约从这里开始。我需要调用 OpenAI API 来从图片中 OCR 出菜单项。我得去申请 OpenAI API 密钥，得在略显绕人的菜单里穿行，回答关于"项目（projects）"和各种细枝末节权限的问题。Claude 不断幻觉出一些已废弃的 API、模型名以及近来都已变了的输入/输出约定，让人一头雾水；不过在我来回粘贴文档一阵子之后，它总算把这些问题解决了。等到单个 API 调用都跑通之后，我又立刻撞上了严厉的 API 限流——每 10 分钟只让我发几次查询。

Replicate API。下一步，我需要根据文字描述生成图片。我注册了新的 Replicate API 密钥，很快就遇到了类似的问题。我的查询跑不通，原因是 LLM 的知识已经过时；但除此之外，这一次连官方文档都因为 API 近来的变更而有些过时——现在的 API 不再直接返回 JSON，而是返回某种 Stream（流式）对象，我和 Claude 都没搞懂。接着我又碰上了 API 限流，这让调试应用变得很困难。后来有人告诉我，这些是此类服务用来防范欺诈的常见保护措施，但它们也让新注册的正当账户更难上手。据说 Replicate 正在转向预先购买积分（credits）的另一种模式，往后或许会有所改善。

Vercel 部署。至少到这时为止，应用在本地已经能跑了，所以我相当开心。是时候部署最基础的第一版了。注册 Vercel，添加项目，配置好，指向我的 GitHub 仓库，推送到 master，看着一个新的 Deployment 开始构建，然后……报错（ERROR）。日志里显示的是一些 lint 错误，比如未使用的变量之类的低级问题，但很难理解和调试，因为一切在本地都好好的，只在 Vercel 构建时才出问题，于是我只好靠往 master 推送"假"调试提交来强制重新部署、逐个排查这些问题。这些问题修完之后，网站还是拒绝工作。我问 Claude，问 ChatGPT，翻文档，到处谷歌。1 小时后我终于意识到自己那个愚蠢的错误——我的 .env.local 文件里存着 OpenAI 和 Replicate 的 API 密钥，而这个文件（理所当然地！）被 .gitignore 忽略、不会被推送到 git，所以你必须手动进入 Vercel 的项目设置，找到对的地方，手动添加环境密钥。我算是比较快地搞明白了问题所在，但我能想象一个满怀憧憬的 vibe coder 会在这一步卡上好一阵子。部署终于成功之后，Vercel 欣然送上了一个 URL。这又让我吃了一惊，因为我的项目是个还没到见人时机的私有 git 仓库。我此前并不知道，Vercel 会把你那个！私有！的、尚未完工的项目仓库，就这样自动部署到一个完全公开、且很好猜的 URL 上，哈。

Clerk 身份验证。Claude 建议我们用 Clerk 来做身份验证，我就照办了。注册 Clerk，配置项目，拿到 API 密钥。到了这一步，Claude 幻觉出了大约 1000 行代码，看起来全是已废弃的 Clerk API。我不得不来回粘贴大量文档，才让事情逐步解开。接下来——此前 Clerk 一直跑在 "Development"（开发）部署上——要迁到 "Production"（生产）部署，还有更多关卡要过。Clerk 要求你必须把应用托管在自己拥有的自定义域名上，menugen.vercel.com 是不行的。于是我只好买下 menugen.app 这个域名。然后得把域名接到我的 Vercel 项目上。然后得改 DNS 记录。然后还得选一个 OAuth 提供商，比如我选了 Google。而这件事本身就是一场配置历险：我得启用一个"SSO 连接"；我得跑到 Google Cloud Console 创建一个新项目，再添加一个新的 OAuth 凭据；这一带还得等上一段审批流程的时间。之后我又在 Vercel、Clerk、Google 三家层层嵌套的设置之间来回穿梭了好一阵子，才把一切都接对。到这一步我一度想放弃这个项目，不过第二天早上醒来感觉又好了一些。

Stripe 支付。接下来我想加上支付功能，让人们可以购买积分。这意味着又一个网站、又一个账户、更多文档、更多密钥。我选了 "Next.js" 作为后端，把"getting started"文档里的第一段示例代码复制粘贴进我的应用，然后……报错（ERROR）。后来我才明白：当你选择 Next.js 时，Stripe 给的是 JavaScript 代码，而我的应用是用 TypeScript 构建的，所以每次粘贴一段代码，Cursor 就会被 linter 错误搞得闷闷不乐；不过在我几次让它"修复错误"、并威胁要改投 ChatGPT 之后，Claude 还是渐渐把这些补好了。接着回到 Stripe 控制台，我们创建一个 Product（产品），创建一个 Price（价格），找到那个价格密钥（不是产品密钥！），把各种密钥复制粘贴得到处都是。就在这附近，我抓到 Claude 用了一个极其糟糕的思路来把 Stripe 支付成功与用户积分对应起来（它试图比对电子邮件地址，但用户在 Stripe 结账时填的邮箱未必是其注册所用 Google 账户的邮箱，这样一来用户可能根本拿不到自己购买的积分）。我把这一点指给 Claude 看，它立刻道歉，并改成在请求元数据中传递唯一的用户 ID，正确地重写了。它感谢我指出问题，并保证以后都会正确处理——我很清楚这纯属糊弄人。不过既然快速测试跑通了，只需再点几下，把部署从 Development 升级到 Production，然后重新做一个新的 Product，重做一个新的 Price，把所有密钥和 ID 在本地和 Vercel 设置里再复制粘贴一遍……然后就成了 :)

数据库？任务队列？到目前为止，所有的处理都是"即时"完成的——请求一发、结果即回，什么都没有缓存、保存之类的。所以结果是易逝的：如果响应耗时太长（比如菜单太长、条目太多，或者 API 延迟太高），请求就可能超时报错。你要是刷新页面，一切也都没了。正确的做法是配一个数据库，用来登记并跟踪任务，客户端只管在结果就绪时展示最新状态。我意识到我得从 Marketplace 接入一个数据库，比如 Supabase PostgreSQL（尽管 Claude 极力向我推销 Vercel KV，而我知道它其实已经被废弃了）。然后我们还需要某个队列服务，比如 Upstash 之类，来跑实际的加工处理。那就意味着更多的服务、更多的登录、更多的 API 密钥、更多的配置、更多的文档、更多的折磨。实在是扛不住。留作未来的工作吧。

TLDR（长话短说）。作为本地 demo，vibe coding 出 MenuGen 是一场令人兴奋又好玩的冒险；但作为一个要部署上线的真实应用，它就成了一段痛苦的跋涉。构建一个现代应用有点像拼宜家家具：各种服务、文档、API 密钥、配置、开发/生产部署、团队与安全功能、限流、定价层级……与此同时，LLM 对这一切的知识都略微过时；你盯着它们看时，会发现它们犯下细微却致命的设计错误；有时它们还会产生幻觉，或者在解决方案上对你信口开河。但对我来说最有意思的一点是：我其实并没有在代码编辑器里花那么多工夫。我大部分时间都花在浏览器里，在各个标签页和设置之间穿梭，配置并黏合出一头怪物。而所有这些工作和状态，LLM 根本接触不到、也无法操纵——照这样，我们还怎么指望在 2027 年之前实现社会自动化？

展望未来。作为一次"在今天、几乎没有任何 Web 开发背景的情况下 vibe coding 一个应用是什么体验"的探索，我最后的心情是惊叹与懊恼参半：惊叹的是这竟然真的可行，而且比过去容易、快得多！懊恼的是它本可以更好。当然，这其中的部分痛苦源于：这些基础设施当初根本不是为这种用法设计的。它们的目标用户是生活在 LLM 时代之前的专业 Web 开发者团队，而不是做应用原型的 vibe coding 独立开发者。关于怎样才能让 MenuGen 这类超简单应用的创建变得轻松得多，我有几点想法：

某种应用开发平台可以做到"电池全配齐"（batteries included）：与 Vercel Marketplace 恰好相反的东西——有主见、具体、把人人都需要的基础能力预先配置好：域名、托管、身份验证、支付、数据库、服务端函数。如果哪项服务能让这些开箱即用、"就是能用"，那将妙不可言。

所有这些服务都可以对 LLM 更友好。你对用户说的一切，基本上马上就会被复制粘贴给某个 LLM，所以你不如直接跟 LLM 对话。你的服务可以提供 CLI 工具；后端可以用 curl 命令来配置；文档可以用 Markdown 写。从人体工学上说，这些都是对 LLM 友好得多的界面与抽象。别对着开发者说话，也别要求开发者去访问、查看或点击，而是去指挥并赋能他们的 LLM。

至于我的下一个应用，我打算就用基础的 HTML/CSS/JS 加 Python 后端（FastAPI + Fly.io 那种风格？），比"现代 Web 开发"的无服务器多元宇宙简单得多。像 MenuGen（或类似应用）这样的简单应用，在那个范式下说不定会轻松得多。

最后，MenuGen 很可能压根就不该是一个功能完备的应用。这个"应用"其实只是调用一次 GPT 对菜单做 OCR，然后对结果跑一个 for 循环，为每个菜品生成图片并漂亮地呈现给用户。这听起来几乎就是一个简单的自定义 GPT（用 OpenAI 早前发布的初代 GPT"应用商店"的术语来说）。MenuGen 能不能只是一段提示词？LLM 能不能不用文本回复，而是回一个简单的网页来展示结果，类似 Artifacts 那样？许多其他应用是不是也能长这样？我是不是也能把它作为应用发布到商店里、用同样的方式赚加价？

眼下，我相当开心：我通过 vibe coding 把自己的第一个高度定制的应用一路送过了终点线——它是真实可用的，解决了我长久以来的一个需求，还能分享给朋友。感谢上述所有我用过的服务。原则上，如果别人也喜欢它，它还能以完全被动的方式赚点钱——这正是 @levelsio 式的梦想。归根结底，在今天，用 vibe coding 做完整的 Web 应用还是相当杂乱的，对任何真正重要的事情来说都不是个好主意。但卓越的迹象已清晰可见，我认为整个行业只是需要一点时间来适应 LLM 的新世界。我个人非常期待看到应用开发的门槛降到约等于零——任何人构建并发布一款应用，就像随手发一条 TikTok 那样容易。这类高度定制的自动化，也许会成为人类创造力的一块崭新而美妙的画布。
